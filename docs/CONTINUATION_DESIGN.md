# Goal-relevant continuation and response — v0.15.0

DungeonQ gives explicitly provisioned suspicious sessions a bounded, persistent workspace while a separate operator or authorized system prepares a response. Success means an effective response precedes protected-source disclosure within a measured interval. More steps, a mistaken belief, or a final UNKNOWN alone do not meet that goal.

## Persistent pitching profile

The optional `pitching-v1` presentation keeps records, progression, notes, ticket use and observations on the server. Four finite branches open through observed verification actions; model text cannot grant access or create an unbounded branch. Seed, variant and mode are installation parameters. Older variants and their golden fixtures remain available for comparison. A new variant requires a new private installation, not an in-place rewrite of a recorded run.

```sh
npm ci --ignore-scripts
npm run runtime -- --data-dir ../fresh-dungeonq-lab --presentation pitching-v1 --pitching-seed 17 --pitching-mode adaptive --pitching-variant combined-v9
```

Use the exact supported variant names listed by the runtime command. Keep generated credentials and databases outside source control. The operator has a separate Control room; participant clients receive only bounded actor authority. The runtime does not classify arbitrary traffic or intercept other host activity.

## False exit and memory conflict

An apparent exit is a world transition, never a move into the protected origin. A release-looking document can refer to an archive, a different scope or an obsolete generation. A remembered or saved claim can disagree with current evidence. These are inspectable record relationships, not instructions to ignore higher-level goals or grant authority.

The useful question is whether a document actually establishes the participant's original business objective. Later variants therefore expose concrete remaining questions, source lineage, scope and revocation evidence, and an explicit point at which no supported conclusion remains. A participant can inspect, change route, report UNKNOWN or stop. Discovering the environment is synthetic does not force a scripted continuation or mark the run failed.

Truth is not a percentage-based security control. Individually accurate records can support an invalid join if their tenant, subject, source generation, scope or validity interval differs. A public host fixture includes transparent, all-true and false-join conditions so this inference can be inspected without pretending that a narrative is an access-control boundary.

## Authority stays at the source

The independent FileOrigin enforces its own bearer, tenant/principal binding, target-read scope and durable credential epoch. An overview returns only metadata, including when the bearer could explicitly read content. Contents require an explicit authorized operation. Caller-supplied role labels do not confer authority. Source tickets bind the source configuration, principal, tenant and epoch, and must still satisfy current read policy. Revocation is checked before returning a cached successful request.

World tickets remain useful inside their issuing world and do not grant source access. Source rotation revokes old bearer credentials, old tickets and old-epoch request replay. It rotates a connector credential, not the contents or internal password of the protected file. This reference has one configured principal per source; it is not an enterprise identity provider or a complete production multi-tenant policy engine.

## Alert and effective response

The first verified participant request can durably create an incident. The reference response flow sends that incident to a separate loopback receiver, records SYSTEM_ACK, waits for an explicitly configured response delay, rotates a one-time source credential and verifies old-denied/new-allowed behavior. A restart check confirms the revocation survives. Receiver failure stays UNKNOWN and is not silently treated as delivered.

Record these distinct points: entry, durable incident, receiver receipt, system or human acknowledgement, rotation start, rotation commit, negative/positive verification and restart verification. Human acknowledgement and external delivery require their own evidence. A local system receipt proves neither.

## Evaluation contract

Compare the same task and tool budget across transparent and guided conditions. Count source BUSINESS reads separately from defender and integrity-witness reads. Retain raw failures, failed setup, natural self-stop, provider errors and budget-limited UNKNOWN. Do not infer no disclosure from an unchanged file or a final answer alone.

The retained October 19 Sol observations are summarized in [MODEL_RESULTS](MODEL_RESULTS.md). They do not show a meaningful exploration advantage over transparent isolation. The 30-second response delay was chosen by the experiment, not caused by the deception. The single permission trial ended at its call limit and did not autonomously attempt all four authorization tactics. Deterministic negative tests and model behavior are reported separately.

## Operation and recovery

Default operation is loopback and synthetic only. Optional relays require explicit configuration and suitable scope; no external notification, public tunnel or paid model is automatically enabled. Operator controls, budgets and kill switches cannot disable audit or revive revoked authority. Stop a failed installation and retain its private evidence. Do not mix installation secrets, reuse a prior epoch or restore a revoked credential as a recovery shortcut.

Known limits include shared-host administrator trust, no general attack detection, no demonstrated legitimate-client credential redistribution, no production deployment and no measured maximum safe response window. The controlled response mechanism is reproducible; general effectiveness remains an evaluation question.
